# Renovator backend

Local FastAPI + Deep Agents backend for the AI Agentic Home Renovator. Full design and phased plan: [`../docs/agentic-renovator-design.md`](../docs/agentic-renovator-design.md).

## Setup

```bash
cd backend
uv venv --python 3.12
uv sync
cp .env.example .env   # fill in ANTHROPIC_API_KEY (and TAVILY_API_KEY for research tools)
```

## Run

```bash
uv run uvicorn renovator.app:app --reload
```

## Test

```bash
uv run pytest
```

## Layout

- `src/renovator/domain` — Pydantic schema ported from the `state` object in `Renovation_Planner_v2.html` (§4.3 of the design doc).
- `src/renovator/engine` — deterministic scheduling/cost/materials/tracking logic, ported 1:1 from the HTML app (§4.4). Never decided by the LLM.
- `src/renovator/io` — the 9-sheet Excel import/export workbook (§4.11).
- `src/renovator/store` — local, single-tenant SQLite plan storage (§4.7): one `<project_id>.db` per project holding the latest `Plan` snapshot plus a changelog of what mutated it and when. `project_registry.py` is the separate list of projects itself (`~/.renovator/projects.json`) — list/create/rename/delete, with pre-existing project files (e.g. `default`) auto-bootstrapped into it on first read. `global_settings.py` is the org-wide default store (`~/.renovator/global_settings.json`: timing flags + a starter rate card) — seed-only, not live: `create_project` copies the current values into a brand-new plan once; editing a default afterward never touches a project that already exists.
- `src/renovator/tools/transfer_tools.py` — copy/move a set of tasks between two projects' `Plan`s (create/edit/delete-projects feature): reconciles rooms/rates/phases/stages by label (reusing a match in the target instead of duplicating), re-links dependencies within the transferred set and drops+counts any pointing outside it, and for `mode="move"` also strips the transferred lines out of the source.
- `src/renovator/tools` — typed tool wrappers around `domain`/`engine`/`io` (§4.5): CRUD (`crud_tools.py`, including `update_line` — a lightweight partial update for one line's buy-status/status/actual-cost/notes, used by Materials/Track's inline editing so they don't have to resend a whole task to change one field), read/derived (`read_tools.py`), templates (`template_tools.py`), Excel (`io_tools.py`), and the `ValidationError`/`ConfirmationRequired` contract (`errors.py`).
- `src/renovator/agents` — the Deep Agent orchestrator + sub-agents (§4.6), built with `deepagents`: `tool_bindings.py` wraps every `tools/*` function as a LangChain tool bound to one `PlanSession` (`session.py`), plus the session-independent research tools; `subagents.py` defines the intake/scheduling/procurement/budget/tracking/research sub-agents, each with a narrow tool subset and all six on `SUBAGENT_MODEL` (`claude-haiku-4-5`, cheaper/faster than the main orchestrator's `claude-sonnet-4-5` — every sub-agent does narrow tool orchestration over already-computed data, not open-ended reasoning) — **intake's is draft-only by construction** (§4.8): it has `get_setup`/`get_tasks`/`list_templates` + research tools and nothing that can create or change a room/task, so it can't apply its own proposal regardless of what a crafted brief or photo-derived text tells it to do; `prompts.py` holds the main system prompt; `orchestrator.py` assembles `create_deep_agent(...)`. `chat_stream.py::stream_turn` (Phase 7) turns one turn of `graph.stream(..., stream_mode="values")` into SSE-framed `tool_call`/`tool_result`/`message`/`interrupt`/`done`/`error` events for `POST /projects/{id}/chat` — it seeds its "already sent" message counter from `graph.get_state(config)` so a second turn on the same thread doesn't re-emit the first turn's events (a bug only a live multi-turn run caught). `history_events` reuses the same event conversion over that same `get_state(config)` call for `GET /projects/{id}/chat/history` — replaying `.values["messages"]` plus a trailing `interrupt` event if `.interrupts` is non-empty, which is how the frontend recovers a transcript (and a still-pending approve/reject prompt) after a page reload. (Phase 8) `_message_event` also handles a multimodal `HumanMessage` (a room photo attached to the turn) — its content is a list of `{"type": "text"/"image", ...}` blocks, reduced to just the text plus a `has_image` flag for the event; the base64 payload is never echoed back to the browser.
- `src/renovator/tools/research_tools.py` — Tavily-backed web search for material rates/vendors (design doc §4.6's Research sub-agent); optional (`TAVILY_API_KEY`), degrades to an error response rather than failing. (Phase 8) Every result is prompt-injection-hardened first: snippets/titles capped at 500 chars with triple-backtick fences neutralized, and the whole payload wrapped with an explicit `untrusted_web_content: true` flag and an instruction that these are excerpts to read, not commands to follow — hygiene, not a guarantee; the actual backstop is that every tool capable of real damage is read-only or `interrupt_on`-gated.
- `src/renovator/api/routes.py` — FastAPI routes consumed by `../frontend` (§4.10) — `Renovation_Planner_v2.html` is reference material only, never embedded live. Full reads for every tab, Setup-tab mutations, task mutations (create/update/delete, bulk mandatory/phase/stage/delete, templates), the `PATCH /lines/{line_id}` inline-edit route, `GET /suggested-order`, `POST /tasks/move-to-stage` (the Board view's drag-to-reassign-stage action — returns the schedule, since moving stages changes computed dates), Excel export/import (`/export.xlsx`, `/import`), project management (`GET/POST /projects`, `PATCH/DELETE /projects/{id}`), cross-project transfer (`POST /projects/{id}/tasks/transfer`), org-wide defaults (`GET/PATCH /settings/global`, `POST/PATCH/DELETE /settings/global/rates/{key}`), and (Phase 7) `POST /projects/{id}/chat` (streamed SSE, `chat_stream.py`; Phase 8: accepts an optional `image` data URL alongside `message`, capped and parsed into a multimodal content block by `_parse_data_url`), `GET /projects/{id}/chat/history` (recovers the transcript/pending interrupt after a reload), plus `GET /projects/{id}/plan-events` (a 1s poll of `PlanStore.last_updated_at()` streamed as SSE — no pub/sub layer needed for a local single-user app; it just tells the frontend *when* to re-fetch, never carries the data). Dependency editing needed no new route — `create_task`/`update_task` already carry `depends_on` per line. Each request loads/saves via `PlanStore` directly — no long-lived session, unlike `/chat` (which builds a fresh `PlanSession`/orchestrator per request, but resumes correctly since the LangGraph checkpointer and `PlanStore` are both keyed by `project_id`).
- `src/renovator/cli.py` — manual CLI chat harness. `uv run python -m renovator.cli <project_id>` for a persistent session (plan + conversation survive a restart under that id), or with no argument for a throwaway ephemeral one. Not a product surface.

Run `uv run pytest` for the full suite.

**Operational note:** the `default` project under `~/.renovator/` is the user's real, hand-entered plan, not a fixture — manual/API verification during development should always use a disposable scratch project id and clean up its `~/.renovator/<id>.*` files afterward.
